# Grill: Package the orchestration (skills, roles, AGENTS.md) as a single pi extension

## Decisions made

- **Single extension at `pi_extensions/orchestrator/`** (renamed from `pi_extensions/subagent/`); the registered tool keeps the name `subagent`: the subagent tool is what discovers roles, so co-locating tool + roles + skills + AGENTS.md avoids cross-extension path resolution (everything resolves relative to the extension's own dir via `import.meta.url`) and collapses three NixOS install options into one.
- **Self-orchestrating repos (end-state 3):** the extension injects the orchestration playbook globally via `before_agent_start`, and the playbook resolves relative to cwd, so every repo that installs the extension is its own hub (its own `projects/`, `areas/`, `archive/`, `resources/`).
- **The injected AGENTS.md is "our way of work" and composes with the repo's own AGENTS.md** rather than replacing it: the extension adds only the generalized orchestration methodology (pipeline, PARA, model discipline, skills/roles); project-specific instructions stay the repo's. The bundled playbook must be pure methodology, not project-specific content.
- **Model registry is per-repo** (`resources/model-registry.md`): full self-containment; the user accepts the per-repo sync cost deliberately.
- **Missing registry is auto-seeded:** the orchestrator runs `pi --list-models`, builds the model table from the configured/logged-in models, fills the rubric + phase-defaults scaffolding from a template bundled in the extension, and tells the user it created the file. Quota/tier/status columns seed as user-edited placeholders because pi cannot know quota. No new extension code; AGENTS.md instructs the orchestrator (it already has bash + write).
- **Spawned workers locate skills via `NIXPI_SKILLS_DIR`:** the subagent tool injects `NIXPI_SKILLS_DIR=<ext>/skills` (resolved via `import.meta.url`) into the worker env alongside `NIXPI_WORKER=1`; roles reference `$NIXPI_SKILLS_DIR/{name}/SKILL.md`. This lets us delete the global skills symlink (`skillsPath`) entirely while keeping the skill file the single source of truth (the worker reads it; nothing is duplicated into the prompt).

## Explicitly ruled out

- **Two extensions** (separate subagent tool + orchestrator content): cross-extension role discovery is fragile; single extension chosen.
- **Copying skills into each repo's `.pi/skills/`**: duplication and drift; skills live once in the globally-installed extension and pi discovers them everywhere via `resources_discover`.
- **Global or hybrid model registry**: per-repo chosen; a single bundled registry rejected.
- **Keeping the global skills symlink (`skillsPath`)** so roles' hardcoded `~/.pi/agent/skills` path keeps working: contradicts the single-extension simplification; replaced by `NIXPI_SKILLS_DIR`.
- **Tool injects skill content into the worker prompt**: duplicates methodology and risks drift (AGENTS.md forbids embedding a skill's methodology in a role); the worker reads the file instead.
- **Per-repo opt-out / kill switch** for the orchestrator: always-on everywhere the extension is installed; YAGNI given end-state 3.
- **Distribution via `pi install` / settings.json packages**: the vector stays the NixOS `extensionsPath` global symlink (matches "repos that leverage this nixos config").

## Open questions (deferred)

- **Does `skillPaths` from `resources_discover` accept a directory of `skills/{name}/SKILL.md` subdirs, or only individual SKILL.md files?** — Planner verifies empirically; fallback is to glob and return each SKILL.md path explicitly (the `dynamic-resources` example passes a single file; `pi --skill` accepts file-or-directory).
- **Is `disable-model-invocation: true` honored for skills served via `resources_discover`** (slash commands work, not auto-invokable)? — Planner verifies; expected to work since it is skill frontmatter independent of discovery source.
- **Exact shape of the bundled registry template** (scaffolding sections beyond the model table) — planner decides, mirroring the current `resources/model-registry.md` structure (rubric, active models, phase defaults, notes).
- **`before_agent_start` appends the playbook to the system prompt vs injects a persistent context message** — planner decides; system-prompt append recommended (instructional content belongs in the system prompt).

## Summary for downstream

Package the orchestration — 7 skills, 4 subagent roles, the AGENTS.md playbook, a model-registry seed template, and the subagent tool — into a single pi extension at `pi_extensions/orchestrator/` (tool stays named `subagent`), installed globally via the existing NixOS `extensionsPath` symlink. The extension serves skills via `resources_discover` from its bundled `skills/` dir, discovers roles from its bundled `roles/` dir (`agents.ts`), injects the generalized "way of work" playbook via `before_agent_start` (composing with any repo-local AGENTS.md), and injects `NIXPI_SKILLS_DIR` into spawned workers so roles reference `$NIXPI_SKILLS_DIR/{name}/SKILL.md`. This is end-state 3 (self-orchestrating repos): the playbook resolves per-cwd, the model registry is per-repo and auto-seeded from `pi --list-models`, and PARA state grows organically per repo. The move deletes the `skillsPath` and `rolesPath` NixOS options and their activation scripts, plus `pi_skills/`, `.pi/agents/`, the `.pi/skills` symlink, and the root `AGENTS.md`; `README.md` and `resources/subagent-orchestration.md` are updated while `resources/lessons/` and `archive/` are left as provenance. The planner must verify `skillPaths` directory semantics and `disable-model-invocation` behavior (see open questions).
