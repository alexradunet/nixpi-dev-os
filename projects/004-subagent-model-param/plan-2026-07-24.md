## Why this matters

Today, changing which model a spawned worker runs on requires editing the
role's frontmatter `model:` field and reverting it afterward. That is slow and
error-prone, and it blocks the motivating use case: a multi-reviewer panel
where parallel reviewers each run on a different model. This plan adds one
optional `model` field to each of the tool's three call shapes (single,
parallel item, chain item) and threads it through the spawn logic so a caller
can override the model per call. The override is pure pass-through: the tool
does no validation, and pi itself rejects a bad value. The effective model is
recorded in the result so usage and cost reporting show what actually ran.

The design is settled in `projects/004-subagent-model-param/grill-2026-07-24.md`.
Treat every decision below as FIXED; do not re-litigate or extend it.

Settled design constraints (from the grill, quoted so you need not open it):

- Precedence: non-empty explicit `model` > role frontmatter `model` > nothing
  (pi default). Effective model = `override?.trim() || agent.model`.
- Push `--model` only when the effective model is truthy.
- Pure pass-through, NO validation against `pi --list-models`; pi errors on bad
  values. Do not add a validation layer.
- Empty/whitespace `model` means "no override" (trim; ignore if empty).
- No enumeration, no state, no aliases. `thinking` and `tools` stay untouched.
- Record the effective model in the result's `model` field.
- Document the param in the tool description and in
  `resources/subagent-orchestration.md`, pointing at `pi --list-models`.
