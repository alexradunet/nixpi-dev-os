## Issues encountered

### 1. Worker env leak broke the smoke tests initially (resolved, not a code defect)

I run as an orchestration worker with `NIXPI_WORKER=1` in my environment. The
smoke-test `pi` subprocess inherited it, so the extension's nesting guard
(`if (process.env.NIXPI_WORKER === "1") return;`) skipped registering the
`subagent` tool. The outer model then reported "I don't have access to a
`subagent` tool" and fell back to `bash`, producing `NO_SUBAGENT_TOOL_CALL`
twice. This is not model flakiness and not a code defect; it is an environment
leak from running the test inside a worker.

Fix: run the child `pi` with the leaked vars unset —
`env -u NIXPI_WORKER -u NIXPI_SKILLS_DIR pi ...` — which restores the clean
shell the plan assumes. With that, the tool registered and both smoke tests ran
for real. The plan's smoke-test commands do not include this `env -u` prefix; a
future runner executing from a normal shell will not need it.

### 2. Step 7 tripped the plan's literal STOP condition; lead ACCEPTED it as satisfied

The plan's Step 7 parser reads the top-level event field `e.isError` and the
worker `exitCode`, and expects `isError=true` + non-zero `exitCode`. It printed
`isError=false`, `exitCode=0`, which matches the plan's literal STOP condition.
I stopped and reported rather than improvise.

Root cause is a mismatch between the plan's predicted mechanism and this pi
version's actual behavior, NOT a defect in the change and NOT a validation
layer:

- The bogus model passed through unchanged. Result `model` =
  `qwen-token-plan/this-model-does-not-exist-xyz`; the worker's own message
  `model` = `this-model-does-not-exist-xyz`. No rewriting, no rejection inside
  the tool. This is the core thing Step 7 was meant to prove, and it holds.
- pi does not reject an unknown model at process level. stderr:
  `Warning: Model "this-model-does-not-exist-xyz" not found for provider
  "qwen-token-plan". Using custom model id.` pi forwards it as a custom id, so
  the process exits 0 (hence `exitCode=0`).
- The provider rejects it at request time: `errorMessage = 404: ...
  code: model_not_found`, and the worker records `stopReason=error`.
- The tool DOES flag the failure. `isFailedResult` returns true on
  `stopReason === "error"`, so the single-mode path returns `isError: true`.
  In the captured event, `e.result.isError = true` and
  `e.result.content[0].text = "Agent error: 404: {"message":"Model not
  exist.",...}"`. The plan's parser reads `e.isError` (the event envelope,
  which is false because the tool execution itself did not crash) rather than
  the tool's returned `e.result.isError` (true).

**Lead decision (authoritative):** Step 7 is ACCEPTED as satisfied. The design
intent (pure pass-through, no validation; a bad value surfaces as an error) is
met and verified. The plan's predicted mechanism (non-zero `exitCode`, reading
the top-level `e.isError`) was wrong for this pi version; the real signal is the
provider 404 surfacing as the tool's `result.isError=true`. This is a
plan-prediction defect, not a code defect. The code was NOT changed.

### 3. Step 8 doc wording corrected by the lead

The plan's Step 8 draft said a bad value is forwarded to `pi --model`, "which
errors with its own available-model list." That is inaccurate for this pi
version (pi does not error or print a model list; it warns and forwards a custom
model id, and the provider 404s). The lead supplied corrected wording, which is
what was committed: the value is pure pass-through, valid strings come from
`pi --list-models`, a bad value is forwarded unchanged to `pi --model`, pi
passes it to the provider which rejects it (`model_not_found`), and the tool
surfaces the failure as an error (`isError=true`, worker `stopReason=error`).
