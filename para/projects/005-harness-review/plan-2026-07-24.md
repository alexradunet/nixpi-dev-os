## Why this matters

Two independent reviews of this repo's orchestration harness converge on the
same verdict: one real security gap and three real correctness bugs, plus
systemic standards debt. The project-agent confirmation gate — the trust
boundary for repo-controlled agent files — evaporates in headless mode
(`ctx.hasUI` false), and this box runs paseo, a non-interactive daemon, so
headless is a normal runtime, not an edge case. The subprocess path reports a
signal-killed worker as success, discards spawn errors entirely, and corrupts
multibyte UTF-8 at chunk boundaries. None of it is tested. The 1053-line
`index.ts` blocks safe refactoring of exactly the code that needs fixing.
After this plan: the gate fails closed, dead workers are reported as failures
with a reason, streaming is encoding-safe, the task no longer leaks via `ps`,
the pure logic has a headless regression suite, and every file is under 500
lines.

### Finding 1 (WS1) — headless gate fails open, `index.ts:540`

```ts
if ((agentScope === "project" || agentScope === "both") && confirmProjectAgents && ctx.hasUI) {
```

When `ctx.hasUI` is false the whole block is skipped: project-local agents
run unconfirmed, with the full parent environment (`index.ts:355`:
`env: { ...process.env, NIXPI_WORKER: "1", NIXPI_SKILLS_DIR: SKILLS_DIR }`).
The block body (`index.ts:540-563`) collects requested agent names, filters to
`source === "project"`, and calls `ctx.ui.confirm(...)`; on "no" it returns a
canceled result. `confirmProjectAgents` defaults to `true`
(`params.confirmProjectAgents ?? true` at `index.ts:511`).

### Finding 2 (WS2) — signal death masked as success, `index.ts:407-409`

```ts
proc.on("close", (code) => {
    if (buffer.trim()) processLine(buffer);
    resolve(code ?? 0);
});
```

`close` passes `(code: number | null, signal: NodeJS.Signals | null)`. On a
signal death (OOM killer, external `pkill`) `code` is `null`, `code ?? 0`
resolves `0`, and `isFailedResult` (`index.ts:195`) returns false: a dead
worker renders with a green check and `(no output)`. The intentional-abort
path is covered separately by `wasAborted` (`index.ts:430`).

### Finding 3 (WS2) — spawn errors discarded, `index.ts:412-414`

```ts
proc.on("error", () => {
    resolve(1);
});
```

The `Error` argument (ENOENT for a missing `pi` binary, EACCES, …) is dropped.
The caller sees `Agent failed: (no output)` with no way to distinguish "model
errored" from "binary not installed". The `errorMessage` field already exists
on `SingleResult` (`index.ts:172`) and already flows through
`getResultOutput` (`index.ts:199-203`) into result rendering — the plumbing is
done; only the capture is missing.

### Finding 4 (WS2) — multibyte corruption at chunk boundaries, `index.ts:396-405`

```ts
proc.stdout.on("data", (data) => {
    buffer += data.toString();
    const lines = buffer.split("\n");
    buffer = lines.pop() || "";
    for (const line of lines) processLine(line);
});

proc.stderr.on("data", (data) => {
    currentResult.stderr += data.toString();
});
```

`Buffer.toString()` on a chunk ending mid-codepoint emits U+FFFD and the next
chunk's leftover bytes decode as U+FFFD too: the boundary character is
destroyed. A corrupted JSON line either fails `JSON.parse` (silently dropped
by `processLine`'s `catch { return; }` at `index.ts:362-365`) or parses with a
mangled string. `StringDecoder` from `node:string_decoder` buffers incomplete
multibyte sequences across chunks. The stderr instance has the same bug
(display-only, lower blast radius) and additionally grows without bound
(`currentResult.stderr +=` is uncapped).

### Finding 5 (WS2) — task content visible in `ps`, `index.ts:346`

```ts
args.push(`Task: ${task}`);
```

The system prompt is protected via a `0o600` temp file
(`writePromptToTempFile`, `index.ts:252-260`, passed as
`--append-system-prompt tmpPromptPath` at `:343`), but the task is a raw argv
element, readable by any local user via `ps aux` / `/proc/<pid>/cmdline`.
Tasks routinely contain paths, code, and pasted context.

**CLI investigation (done during planning)**: pi 0.81.1 has no
`--prompt-file` flag, but its CLI is `pi [options] [@files...] [messages...]`
and `@file` positionals include file contents in the initial message
(documented in pi `docs/usage.md:251-256`, mode-independent; example:
`pi @prompt.md "Answer this"`). Separately, print mode merges piped stdin into
the initial prompt (`docs/usage.md:176`). The `@file` mechanism is the primary
fix (mirrors the existing temp-file pattern); stdin is the documented fallback.

### Finding 6 (WS3) — no test suite

No `package.json` anywhere in the repo; no test runner configured. `bun` is
not on PATH (pi's bun is embedded in its nix-store binary). Node v24.18.0 is
installed (`nodejs_24` in `configuration.nix` systemPackages).

**Runner investigation (done during planning, verified in a /tmp scratch
dir)**: `node --test` on Node 24 discovers `*.test.ts` files, runs them with
native TypeScript type-stripping, and — critically — type-only imports
(`import type { Message } from "@earendil-works/pi-ai"`) are erased without
module resolution, so a module with zero runtime pi imports is testable under
bare `node` even though `@earendil-works/*` packages are only resolvable
inside pi's bundled runtime. A scratch suite using exactly the
`StringDecoder` pattern and `assert/strict` passed: `node --test` → 2 pass,
0 fail. Decision: **`node --test pi/orchestrator/`** — zero new machinery,
zero dependencies, headless, single command.

Consequence for module layout: the tested helpers must live in a module with
**no runtime imports from `@earendil-works/*` or `typebox`** (type-only
imports are fine; `node:` builtins are fine). This module is `core.ts`,
created in WS1 and the unit-test seam for the whole plan.

#### Step 1.1: Create `pi/orchestrator/core.ts` with the pure gate decision

Create `pi/orchestrator/core.ts`. Module contract: **zero runtime imports
from `@earendil-works/*` or `typebox`** — type-only imports and `node:`
builtins only. This is what makes the module testable under bare `node`
(see Finding 6). Header comment must state this contract.

Add the gate decision. Exact shape:

```ts
import type { Message } from "@earendil-works/pi-ai";
import type { AgentConfig, AgentScope } from "./agents.ts";

/**
 * Pure core logic for the subagent tool: result classification, output caps,
 * exit/signal outcome, the project-agent trust gate, stream line splitting,
 * concurrency mapping. No runtime imports from @earendil-works/* or typebox —
 * this module is the unit-test seam (node --test runs it under bare node).
 */

export type ProjectAgentGateDecision =
	| { action: "proceed" }
	| { action: "confirm"; agents: AgentConfig[]; dir: string | null }
	| { action: "reject"; agents: AgentConfig[]; dir: string | null };

/**
 * Decide whether project-local agents may run. Trust boundary: headless
 * sessions cannot prompt, so they fail closed unless the caller explicitly
 * opted out with confirmProjectAgents: false.
 *
 * Example: decideProjectAgentGate({ agentScope: "both", confirmProjectAgents: true,
 *   hasUI: false, requestedAgentNames: ["impl"], agents, projectAgentsDir: dir })
 * → { action: "reject", ... }
 */
export function decideProjectAgentGate(opts: {
	agentScope: AgentScope;
	confirmProjectAgents: boolean;
	hasUI: boolean;
	requestedAgentNames: string[];
	agents: AgentConfig[];
	projectAgentsDir: string | null;
}): ProjectAgentGateDecision {
	if (opts.agentScope === "user" || !opts.confirmProjectAgents) return { action: "proceed" };
	const requested = new Set(opts.requestedAgentNames);
	const projectAgents = opts.agents.filter((a) => requested.has(a.name) && a.source === "project");
	if (projectAgents.length === 0) return { action: "proceed" };
	if (!opts.hasUI) return { action: "reject", agents: projectAgents, dir: opts.projectAgentsDir };
	return { action: "confirm", agents: projectAgents, dir: opts.projectAgentsDir };
}
```

(The `Message` import is unused until step 2.3 adds result helpers; if your
tooling warns, add the rest of the WS2 helpers in the same pass — but commit
per workstream as specified.)

**Verify**: `node -e "import('./pi/orchestrator/core.ts').then(m => console.log(typeof m.decideProjectAgentGate))"` → prints `function`, exit 0. (Proves syntax, type-stripping, and the no-runtime-deps contract all hold.)

Add to `core.ts`:

```ts
import { StringDecoder } from "node:string_decoder";

/**
 * Split a byte stream into lines, buffering incomplete UTF-8 multibyte
 * sequences across chunk boundaries (Buffer.toString() per chunk would emit
 * U+FFFD at boundaries). push() per chunk, flush() once at stream end.
 */
export function createLineSplit(onLine: (line: string) => void) {
	const decoder = new StringDecoder("utf8");
	let buffer = "";
	return {
		push(chunk: Buffer): void {
			buffer += decoder.write(chunk);
			const lines = buffer.split("\n");
			buffer = lines.pop() || "";
			for (const line of lines) onLine(line);
		},
		flush(): void {
			const tail = buffer + decoder.end();
			buffer = "";
			if (tail.trim()) onLine(tail);
		},
	};
}

export const STDERR_CAP_BYTES = 64 * 1024;

/**
 * Cap accumulated stderr, keeping the TAIL (errors land at the end) and
 * dropping the head with a marker. Byte-aware so the cut never splits a
 * multibyte character.
 */
export function capStderr(stderr: string, cap: number = STDERR_CAP_BYTES): string {
	const bytes = Buffer.byteLength(stderr, "utf8");
	if (bytes <= cap) return stderr;
	let tail = stderr.slice(-cap);
	while (Buffer.byteLength(tail, "utf8") > cap) tail = tail.slice(1);
	return `[stderr truncated: ${bytes - Buffer.byteLength(tail, "utf8")} bytes dropped from head]\n${tail}`;
}
```
