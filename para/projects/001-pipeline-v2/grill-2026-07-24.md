# Grill: Orchestration Pipeline v2

## Decisions made

- **Grill absorbs explore**: Grill is the single entry point for features and bugs. It already has read-only codebase access; for bugs, it investigates root cause as part of grilling. Explore is removed as a pipeline phase but survives as an ad-hoc tool outside the pipeline. Rationale: even reporting a bug requires codebase exploration; two entry points added routing complexity for no gain.

- **Everything downstream of grill is a spawnable worker**: spec, domain-model, plan, tickets, implement, review are all spawned via `paseo run`. Workers communicate through artifacts on the filesystem. Rationale: consistent execution model, isolated context windows, parallelizable.

- **Workers are multi-turn**: The orchestrator relays user input via `paseo send`. The user can open any worker directly via `paseo agent open` for hands-on steering. Workers report `blocked` status when they need input. Rationale: full user control over sub-agents without sacrificing the artifact contract.

- **Domain modeling is hybrid (bootstrap + flag + reconcile)**: A domain-model worker runs after spec to bootstrap `CONTEXT.md` and ADRs. All other role briefings include a standing instruction to read `CONTEXT.md`, use its vocabulary, and flag contradictory or new terms in their artifact (not edit `CONTEXT.md`). A domain-model-close worker runs at project close to reconcile flagged terms. Rationale: single authoritative author prevents glossary drift; flagging catches what the bootstrap missed.

- **Plan and tickets are separate phases**: Plan produces the architecture (modules, interfaces, schema, API contracts, testing strategy — the "how"). Tickets reads the plan and slices it into vertical tracer bullets with blocking edges and acceptance criteria (the "who does what in what order"). Rationale: different questions, different artifacts. The plan is also useful outside the pipeline for onboarding and review context.

- **Parallel implement with TDD baked in**: Each ticket gets its own implement worker in its own worktree. TDD discipline (red-green per step, test at the spec's seams) is part of the implement role briefing, not a separate phase. Rationale: TDD is how you implement, not a separate step; the spec's test seams section drives where tests go.

- **Branching: off main by default, integration branch for shared files**: Independent tickets branch off `main` (`NNN-slug/ticket-NN`). When the tickets worker flags shared blast radius (tickets touching the same files), use an integration branch with a final integrate-and-verify ticket. Rationale: simplest strategy that works; escalate only when needed.

- **Review at two levels**: Per-ticket Standards review (code smells, repo conventions) runs after each implement worker finishes. Per-feature two-axis review (Standards + Spec conformance) runs after integration. Rationale: standards violations are local and cheap to catch early; spec conformance is global and only makes sense when the feature is assembled.

- **Ticket files are the state machine**: Each ticket file (`para/projects/{NNN}/tickets/NN-slug.md`) carries frontmatter with `status: blocked|ready|in-progress|review|done`, `worker: <agent-id>`, and `branch: <branch-name>`. The orchestrator scans the directory to compute the frontier. No separate state file. Rationale: flat files are the PARA way; single source of truth, grep-able, git-trackable.

- **Grill stays in-session**: Grill is the one phase where the user is the source of truth and the conversation is the point. Spawning it adds relay latency for no artifact quality gain. Rationale: tight Q&A loop, decisions belong to the user.

## Explicitly ruled out

- **Separate explore pipeline phase**: Absorbed into grill. Two entry points added routing complexity; grill already has codebase access.
- **One-shot workers**: Workers are multi-turn via `paseo send` and `paseo agent open`. One-shot was too restrictive for interactive checkpoints (e.g., spec confirming test seams).
- **Domain modeling as a single spawnable phase only**: Would leave the glossary stale when implement discovers new terms. Hybrid approach catches more.
- **Domain modeling as embedded discipline only**: No single author means glossary drift. Needs an authoritative bootstrap + reconcile pass.
- **Separate state file for ticket tracking**: A `pipeline-state.json` alongside ticket files creates a second source of truth that drifts. Ticket frontmatter is sufficient.
- **Review only at feature level**: Late feedback lets bad code enter the integration branch. Per-ticket standards review catches problems early.
- **Review only at ticket level**: Spec conformance can't be assessed on a partial slice. Needs the full feature.
- **Plan subsumed by tickets**: The plan (architecture) is a distinct deliverable useful for onboarding, review context, and spec input. Tickets are the execution breakdown.

## Open questions (deferred)

- **Output schema extension**: The current worker-output-schema has a single `artifact_path`. The tickets worker produces a directory of files. May need a `artifacts` array or use the directory path. Decide during implementation.
- **CONTEXT.md location**: The domain-modeling skill says repo root. Confirm this works with worktrees (each worktree gets its own copy via git). Decide during implementation.
- **Explore skill/role disposition**: Keep as ad-hoc tool, fold into grill skill, or remove. Decide during implementation.
- **Model tiers per phase**: New phases (spec, domain-model, tickets) need tier assignments in the model registry. Decide when writing role briefings.

## Summary for downstream

Pipeline v2 replaces the 4-phase pipeline (explore → plan → implement → review) with a 10-phase pipeline: grill (in-session, absorbs explore) → spec → domain-model → plan → tickets → implement (parallel, TDD) → review-standards (per-ticket) → integrate (conditional) → review-feature (two-axis) → domain-model-close. All phases after grill are spawnable Paseo workers communicating through filesystem artifacts. Ticket files carry their own state in frontmatter. Domain modeling is hybrid: bootstrap after spec, flag-only in all workers, reconcile at close. Branching is off main by default, integration branch when tickets share files. The spec artifact (adapted from Matt Pocock's to-spec skill) and ticket format (adapted from to-tickets) are the primary new artifact types. TDD is baked into the implement role briefing. Review runs at two levels: per-ticket standards, per-feature two-axis (Standards + Spec).
