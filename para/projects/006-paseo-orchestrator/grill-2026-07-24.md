# Brief 006: Full Paseo orchestration (retire the pi subagent tool)

## Idea

Replace the extension's custom `subagent` tool (one-shot `pi` subprocesses) with
the Paseo daemon as the sole spawn layer. Pi stays the interactive orchestrator
(playbook + skills + PARA); Paseo provides worker lifecycle, worktree
workspaces, visibility, and cross-provider reach. One orchestrator: Pi + Paseo.
If pi-native subagents are ever wanted again, install an existing
battle-tested community extension — we do not maintain our own.

Grilled and locked in-session on 2026-07-24. All five decisions below are
confirmed by the user; the plan must implement them as stated, not re-debate them.

## Locked decisions

1. **Extension shape: hooks only.** Delete the `subagent` tool and everything
   that exists solely to serve it: `spawn.ts`, `render.ts`, `format.ts` (+ its
   test), `agents.ts`, the tool half of `core.ts` (+ its test as far as it
   covers deleted code), and the registration block in `index.ts`. What
   survives: the two hooks (`resources_discover` serving `skills/`,
   `before_agent_start` injecting `AGENTS.md`) — currently `index.ts:86-91`.
   `index.ts` should end up ~30-60 lines. Keep only pure helpers that the
   hooks genuinely need; delete the rest.

2. **Spawn semantics: foreground for short phases, background for implement.**
   Orchestrator drives Paseo via bash (pi has no MCP client by design;
   `usage.md:309`).
   - explore/plan/review: `paseo run --wait-timeout 30m --output-schema ...`
     (blocks, returns structured summary).
   - implement: `paseo run --background` → agent ID; then either
     `paseo wait <id>` or a self-heartbeat
     (`paseo heartbeat create "check worker <id>; read its artifact" ...`)
     so the orchestrator can free the session and report back.
   - Redirects use `paseo send <id> "follow-up"` instead of spawning fresh
     workers.

3. **Worktrees: Paseo-managed.** Drop the playbook's hand-rolled
   `git worktree add ../<repo-dir>-{NNN}-{slug}`. Use:
   `paseo workspace create --isolation worktree --worktree-mode branch-off --new-branch {NNN}-{slug} --worktree-slug {NNN}-{slug} --base main`
   then `paseo run --workspace <id>`. Worktrees land under
   `~/.paseo/worktrees/<hash>/<slug>/`. Add a `paseo.json` setup hook at repo
   root only if the worktree demonstrably needs one (verify; this Nix flake
   likely needs none).

4. **Artifacts travel with the worker.** Workers write to
   `para/projects/{NNN}-{slug}/` in their own cwd (main checkout for
   explore/plan; worktree for implement/review). The orchestrator reads them
   at the worker's path (from `paseo inspect <id>`). Implement artifacts merge
   back with the branch. One convention, no env-var tricks.

5. **Adopt now: heartbeats + follow-ups. Defer (YAGNI): schedules, `paseo loop`,
   committees, chat rooms, browser, voice.** No code or docs for deferred
   features beyond a one-line "future" note.

## Edge case to handle in the playbook

Inside a Paseo session (`PASEO_AGENT_ID` set — the normal case on this box),
`paseo run` auto-parents the worker under the current agent in the current
workspace. Outside one, it creates a top-level agent in a new workspace;
the playbook must then pass `--workspace <id>` explicitly (from
`paseo workspace ls --json` matched on cwd).

## Ordering constraint (critical)

This plan is itself executed through the OLD subagent tool — the implement
worker is spawned by the harness it is replacing. The plan must keep the
extension loadable and the `subagent` tool functional until the final
switchover step: build new roles/playbook/skills alongside first, delete the
tool machinery last, then verify `pi` loads the slim extension (hooks fire,
skills discoverable) and run one smoke `paseo run` delegation. No intermediate
commit may break the harness.
