# Grill: per-call model override for the subagent tool

## Decisions made

- **Core feature is a per-call `model` override**, not a model-enumeration mechanism. The pain being solved is that varying a worker's model today requires editing the role file (and reverting it afterward). Dynamic discovery of available models is a secondary concern, kept minimal.
- **The `model` param applies to all three modes**: single (`SubagentParams.model`), parallel (`TaskItem.model`), and chain (`ChainItem.model`). Uniform, one optional field each. The parallel case is the motivating one — a multi-reviewer panel on different models can run concurrently as a `tasks` array instead of sequential role-file edits.
- **Precedence:** non-empty explicit `model` > role frontmatter `model` > (nothing passed, pi uses its default). Effective model = `override?.trim() || agent.model`; `--model` is only pushed when that is truthy.
- **Pure pass-through, no validation in the tool.** A bad model is forwarded to `pi --model`, which already fails loudly with its own available-model list. A second validation layer is redundant (KISS).
- **Discovery stays manual:** the orchestrator runs `pi --list-models` on demand to learn valid `provider/model` values. No enumeration is baked into the tool or extension.
- **Empty/whitespace `model` means "no override"** — the value is trimmed and ignored if empty, falling back to frontmatter.
- **The effective model is reflected in the result's `model` field** so usage/cost reporting shows what actually ran.
- **Documentation touch only:** add the `model` param to the tool's description and to `resources/subagent-orchestration.md`, noting valid values come from `pi --list-models`.

## Explicitly ruled out

- **A "list models" tool or subagent mode** — discovery is `pi --list-models`, run by hand.
- **Validation of the model against the live list** — pass-through; pi errors on bad values.
- **Model aliases / nicknames / shortcuts** — callers pass the real `provider/model` string.
- **Per-model thinking defaults or auto-tuning** — `thinking` stays an independent, unchanged param.
- **The tool reading the model registry** — `resources/model-registry.md` and the bundled template stay human-curated guidance docs; the tool never reads them.
- **Persisted defaults** (last-used model, per-project model) — no state; each call is explicit.

## Open questions (deferred)

- Exact wording of the tool-description and `subagent-orchestration.md` updates — planner/implementer decides; constrained only by "document the param and point at `pi --list-models`."

## Summary for downstream

Add one optional `model` string field to `SubagentParams`, `TaskItem`, and `ChainItem` in `pi/orchestrator/index.ts`, and thread it through `runSingleAgent` so the effective model is `override?.trim() || agent.model` (push `--model` only when truthy; record it in the result's `model` field). No validation, no enumeration, no state — a bad value is pi's problem, and the orchestrator discovers valid values via `pi --list-models`. Document the new param in the tool description and `resources/subagent-orchestration.md`. `thinking` and `tools` are untouched.
